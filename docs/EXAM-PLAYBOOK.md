## 1. 어디에 입력하는지 먼저 구분한다

| 화면 위치 | 하는 일 | 입력 예 |
| --- | --- | --- |
| 왼쪽 파일 목록·가운데 편집기 | 실제 README·코드·문서 확인 | 파일을 직접 열어 읽기 |
| 아래 Terminal의 일반 셸 | 프로그램 실행 | `codex`, `git clone ...` |
| Terminal 안 OpenAI Codex의 입력란 | AI에게 조사·수정·검증 요청 | README의 시작 요청, `/model`, `$cofa-build` |
| 오른쪽 실무자 에이전트 | 업무 목적·처리 기준 확인 | “결과를 아직 모르는 상태는 어떻게 처리하나요?” |
| Browser | 실제 화면을 본인이 확인 | 과제가 웹일 때 실제 포트·경로 입력 |
| Cofa Helper / 문제 신고 | 사용법 / 반복 장애 해결 | 단계·시각·실제 오류 문구 전달 |

README의 다운로드 단계가 끝났다면 **OpenAI Codex / Ask Codex 칸에 README의 시작 요청을 보낸다.** 일반 셸만 있으면 `codex`를 실행한다. `/model`에서 실제 제공된 허용 모델을 확인한다. 개인 로그인·외부 AI·API 키를 추가하지 않는다. `$스킬명`은 일반 셸 명령이 아니다.

시작 요청은 받은 `.cofa-kit/prompts/SCENARIO.md`와 실제 과제 자료를 읽도록 한다. 필요한 지침은 파일로 읽으므로 스킬 설치 없이도 적용할 수 있다. 도구 권한 창이 나오면 명령과 경로가 요청한 작업인지 본인이 확인한다. 다운로드나 파일 읽기가 실패하면 그 사실을 표시하고 아래 복구표를 따른다.

**첫 답에서 확인할 것:** 실제 과제 안내의 경로, 필수 기능·제출물, 확인 방법, 중요한 업무 질문. `.cofa-kit/README.md`나 합성 예제를 실제 문제로 읽은 답이면 즉시 바로잡는다.

### 승인 대기와 실제 실행을 구분한다

`/status`는 모델·권한 확인, `/model`은 제공 모델 선택이다. 실행할 명령을 묻고 있으면 내용을 확인해 한 번 승인하거나 거절한다. 실행 표시·출력이 이어지는 동안에는 같은 요청을 반복하지 않는다. 서버처럼 계속 실행하는 명령도 있다. Codex의 완료 응답은 기능 검증이나 과제 최종 제출 완료를 의미하지 않는다. [상세 가이드 p.2]

터미널은 `+`로 하나 더 열 수 있다. **Codex 터미널과 서버 터미널을 나눠 쓰면** 서버를 유지하면서 작업하기 쉽다. 탭 이름을 더블클릭해 이름을 바꾸고 필요한 경우 분할한다. Windows/Linux 터미널 붙여넣기는 `Ctrl+Shift+V`, 줄바꿈은 `Alt+Enter`다. 선택된 텍스트가 없는 상태에서 `Ctrl+C`를 누르면 해당 명령을 중단하므로 서버 터미널에서 누르지 않도록 주의한다. 파일 탐색기 목록이 늦으면 탐색기 새로고침을 사용한다.

### Browser는 포트와 경로만 맞춘다

1. Codex에 기존 프로젝트 실행법으로 서버를 `0.0.0.0`에 바인딩해 실행하고 **실제 포트·경로·확인할 동작**을 알려 달라고 한다. `3000`은 예시다.
2. 왼쪽 **Browser**를 열고 **PORT**에 실제 실행 포트를 입력한다.
3. **URL**의 자동 표시 호스트 뒤에 `/` 또는 필요한 `/dashboard` 같은 경로를 넣는다. 외부 주소를 만들거나 터널을 열 필요가 없다.
4. 오른쪽 **원형 화살표**를 누르고 화면의 입력·버튼·이동을 본인이 직접 확인한다. 서버를 재시작했으면 다시 누른다.
5. 기다림 화면이 계속되면 **서버 로그·종료 여부 → 실제 포트 → `0.0.0.0` → 경로** 순서로 점검한다. 화면이 열리기 전의 “아직 응답하는 서버가 없어요”만으로 코드 오류라고 단정하지 않는다.

서버 터미널은 닫지 않는다. 상단 CPU/RAM을 확인하며 같은 서버·테스트·분석을 중복 실행하지 않는다. 정리가 필요하면 본인이 실행한 작업의 프로세스만 식별한다. 플랫폼 연결 프로세스나 감독 프로그램을 종료하지 않는다. 자신의 과도한 프로세스 사용으로 인한 메모리 부족(OOM)은 가이드에서 구제 대상이 아니라고 안내한다. [상세 가이드 pp.2–3, 5]

### 파일 수정 뒤 저장 충돌이 보일 때

| 표시 | 본인이 할 일 |
| --- | --- |
| 저장 중… / 저장됨 | 제출 전 `저장됨`까지 확인. `Ctrl+S`로 즉시 저장 가능 |
| 저장되지 않은 변경 / 저장 실패 | 오류·연결을 확인하고 저장. 화면에 보인다는 이유만으로 디스크에 저장됐다고 가정하지 않기 |
| 외부 변경 감지 / 디스크에서 삭제됨 | AI·터미널이 바꾼 내용과 에디터 내용을 먼저 비교 |
| 외부 변경 불러오기 | 작업 공간 파일에 반영된 AI·터미널의 최신 내용을 편집기로 가져옴 |
| 현재 내용으로 저장 | 편집기 내용을 작업 공간 파일에 씀. AI 수정이 사라지지 않는지 확인 후 선택 |
| 파일명 옆 U / M | 이 에디터에서 U는 접속 후 새 파일, M은 에디터의 미저장 변경. Git 상태와 혼동하지 않기 |

AI와 같은 파일을 동시에 편집하지 않는 것이 키트의 권장 방식이다. 충돌 해결은 본인이 내용을 비교해 선택하며, 해결 뒤 `저장됨`을 다시 본다. [상세 가이드 p.3]

## 2. 결과를 확인하며 같은 대화에서 진행한다

진행은 Codex가 필요한 지침을 골라 적용한다. 본인은 아래 세 가지를 반복한다.

1. **업무 기준을 확인한다.** 답에 따라 구현이 달라지는 질문만 실무자에게 직접 보내고 실제 답변을 Codex에 전달한다. 답을 못 받은 내용은 미확인, 진행을 위해 실제로 선택한 내용은 임시 가정으로 구분한다.
2. **실제 결과를 본다.** 무엇을 바꿨고, 어떤 입력에 어떤 결과가 나왔는지 확인한다. 계획만 있거나 “완료”라는 말만 있으면 실행 결과를 요청한다.
3. **시간과 우선순위를 알려 준다.** 화면의 실제 남은 시간을 전달한다. 반복 오류·필수 실패가 있으면 그것부터 고친다.

구현·검증·시간 부족 때 복사할 짧은 요청은 [README](../README.md)에 모아 두었다. 실무자에게 받은 답변은 그대로 전달하고, 임시 가정과 구분해 달라고 요청한다. 같은 Codex 대화에서 이어가면 된다.

### 실제 문제에 따라 달라지는 준비

| 받은 과제 | Codex가 먼저 할 일 | 본인이 확인할 점 |
| --- | --- | --- |
| 기존 코드·API의 오류 수정 | 기존 실행법·계약·테스트 확인 → 오류 재현 → 최소 수정 → 같은 재현과 회귀 검사 | 원인이 설명되는가? 정상 동작과 API가 유지되는가? |
| 새 기능·서비스 | 기존 스택으로 입력→처리→결과 하나를 완성하고 필수조건 확장 | 고정 예시 화면이 아니라 실제 입력이 처리되는가? |
| CSV·반도체 데이터 | 행 단위·분모·중복/재검·시점·키 관계부터 확인 | 작은 손계산과 일치하는가? 관측 차이를 원인으로 단정하지 않는가? |
| 예측·분류·회귀 모델 | 예측 시점·정답 정의·분할·단순 기준선·평가지표 확인 | 미래 정보가 섞이지 않았는가? 기준선보다 나은지 실제 같은 평가로 확인했는가? |
| 문서·분석·의사결정 | 근거·가정·대안·판단 기준을 확인하고 요구 형식 작성 | 근거와 결론이 이어지는가? 하지 않은 검증을 썼는가? |

기존 프로젝트 과제면 `cofa-build`의 [기존 코드 수정 지침](../skills/cofa-build/references/existing-project.md)을 읽는다. 반도체 과제에만 `cofa-semiconductor`와 [반도체 실습](SEMICONDUCTOR-WALKTHROUGH.md)을 적용한다. 실제 CSV 결합이 필요할 때만 [조인 검사](DATA-JOIN.md)를 쓴다. 새 대시보드나 MCP를 무조건 추가하지 않는다.

실제 예측 모델 과제일 때만 [cofa-model-eval](../skills/cofa-model-eval/SKILL.md)을 추가한다. 기존 키트 실행기로 검사를 기록한다면 선택한 코드·테스트를 `--watch`로 추적해 [이전 검증 이후 변경](TOOLS.md#검증한-파일이-바뀌었는지-확인하기)을 확인할 수 있다. 두 기능 모두 선택형이며 시작 요청이나 제출 순서는 바뀌지 않는다.

공식 사이트의 주문 API 화면은 **공개 시연용 예시**다. 실제 과제 스택·파일명·문제를 예고하지 않는다. 예시의 `DECISIONS.md`를 모든 과제의 필수 파일로 만들지 않는다. 사례와 근거는 [조사 결과](RESEARCH.md)에 있다.

웹 결과물이 필요하면 Codex가 서버를 `0.0.0.0`으로 열고, 본인이 Browser에서 실제 포트·경로를 맞춰 버튼·입력·오류를 확인한다. 서버 터미널을 유지한다. 사람이 관찰한 결과만 전달하며 UI 자동 조작은 사용하지 않는다. 화면이 없는 코드·분석 과제에 Browser를 추가할 필요는 없다.

### 여러 스킬을 같이 쓰고 싶을 때

기본 흐름에서는 필요한 스킬 파일을 직접 읽는다. 이름으로 호출하고 싶은 경우에만 [설치·호출 설명](SKILLS-BEGINNER.md)을 참고한다. 두 스킬을 함께 요청하면 **같은 Codex가 두 지침을 적용**하며, 두 AI의 자동 병렬 실행을 뜻하지 않는다. 설치한 스킬이 예전 버전이거나 이름이 안 보이면 현재 키트의 해당 `SKILL.md`를 직접 읽도록 한다. 설치 충돌을 없애려고 기존 파일을 삭제하지 않는다.

### 시간이 얼마나 남아야 하나

| 과제 시작 후 경과 | 권장 우선순위 |
| --- | --- |
| 0–30분 | 감독 절차, 실제 요구·기존 실행법·중요 업무 질문 |
| 30–115분 | 가장 중요한 흐름부터 구현·검증하고 필수조건 확장 |
| 115–145분 | 오류·경계·회귀 검사, 필요한 화면 수동 확인 |
| 145–170분 | 필수 문서·실행법·한계·본인 이해·저장 확인 |
| 170분부터 | 직접 제출 절차 시작 |

화면의 남은 시간이 우선이다. 늦게 시작해도 23:00은 연장되지 않는다. 서술형 30분, 질문 준비 대기, 업로드 여유를 먼저 남긴다. 대기는 브리프 약 5분, 상세 가이드는 최대 10분과 재시도 가능성을 설명한다. 토큰별 감점 공식은 공개되지 않았으며, 같은 설명·불필요한 문서 읽기·설정을 반복하기보다 실제 검증에 시간을 쓴다.

## 3. 제출 준비와 마지막 단계는 본인이 확인한다

**아직 제출 확정 전일 때** [README의 제출 전 요청](../README.md)을 사용한다. 실제 필수 파일·내용과 구현을 대조하고 정상·오류·경계 검증의 결과, 실패·미검증, 남은 한계를 확인한다. 제출 문서는 실제로 수행한 작업과 관찰 결과에 맞춘다. 화면 확인과 제출 버튼 조작은 본인이 한다.

먼저 [작업 내역 정리](../README.md#작업이-끝나면-무엇을-했는지-보기)에서 실제 구현·AI 활용·본인 판단·검증·한계를 확인한다. 문제·선택 이유·검증 결과·한계를 본인이 설명할 수 있는지 점검하고, 시간이 있으면 **확정 전에만** `cofa-explain` 지침으로 짧게 연습한다. 확정 뒤에도 요약을 열람할 수 있다고 가정하지 않는다. 스크립트가 출력한 PASS나 파일 존재만으로 실제 과제 완료를 판단하지 않는다.

- [ ] 작업 종료 10분 전부터 저장·필수 파일·내용·경로·충돌 표시를 확인한다.
- [ ] 전체 제출 파일 **10GB 이하**인지 확인한다. 필요하면 [로컬 파일·용량 검사](TOOLS.md#제출-전-파일과-용량-확인)를 쓰되, 결과는 디스크 집계이며 플랫폼의 제출 판정은 아니다.
- [ ] 상단 **제출하고 문제풀기**로 미리보기를 연다. 수정이 필요하면 미리보기를 닫고 저장·검증한다. 미리보기 중에도 시간은 흐른다.
- [ ] 제출 미리보기가 전체 파일 목록이 아닐 수 있음을 기억하고 본인이 제출물을 확정한다.
- [ ] **제출물 확정하고 문제풀기**를 누르면 파일을 고칠 수 없다. 숨김 파일·도구 폴더가 미리보기에 없다고 실제 제출에서도 빠진다고 판단하지 않는다.
- [ ] **확정 후 파일 수정·AI·Skill·MCP 사용을 중단한다.**
- [ ] 질문 준비가 끝나면 본인이 시작/문제 풀기를 누른다. 첫 타이머가 시작된다.
- [ ] **6문항×5분**, AI와 복사/붙여넣기 없이 본인이 답한다. 이전 문항으로 돌아갈 수 없고 답 제출 후 다음 시간이 시작된다.
- [ ] 녹화·자료 업로드를 기다리고 완료 화면의 **제출 ID·시각·파일 수·크기**를 확인한 뒤 닫는다.

마지막 문항은 **답안 제출하고 마치기**를 누른다. **“과제가 잘 제출됐어요.”** 완료 표시와 위 정보를 확인한 뒤 종료한다. 최소 응시 시간은 없으며 최종 종료 안내 후에는 23:00까지 기다리지 않아도 된다. [상세 가이드 pp.3–4]

파일 확정만으로 응시가 끝나는 것은 아니다. 반복 오류는 단계·시각·오류를 문제 신고로 전달한다. 문의·재접속으로 타이머가 멈추지는 않는다. 근거: 참가자 브리프 p.1, 상세 가이드 pp.3–5.

## 제출 확정 전에 막혔을 때만 확인

| 증상 | 바로 할 일 |
| --- | --- |
| 공개 키트 다운로드 실패 | [README](../README.md)의 일반 터미널 명령과 현재 과제 폴더 확인. 접근 차단이면 우회하지 않고 Helper/문제 신고, 기본 Codex로 실제 과제 진행 |
| 키트는 있는데 스킬이 안 보임 | `.cofa-kit/skills/cofa-triage/SKILL.md` 같은 실제 파일을 읽게 한다 |
| Python·설치·MCP 문제 | 기본 흐름은 파일 읽기로 계속. 도구가 필요한 경우만 [CLI](TOOLS.md)·[설정](SETUP.md) 확인 |
| 파일 읽기·명령이 정책상 차단됨 | 읽거나 실행됐다고 가정하지 않음. 실제 오류를 Helper/문제 신고로 확인하고 개인 인증·감독 설정을 변경하지 않음 |
| 같은 오류가 반복됨 | [오류 복구 요청](../prompts/RESCUE.md)으로 작은 입력의 기대값·실제값부터 재현 |
| 새 대화·재접속 | [SCENARIO의 재개 요청](../prompts/SCENARIO.md#재개할-때)으로 실제 파일·기록 확인 후 계속 |
| 한 영역만 멈춤 | 표시되어 있으면 **이 영역 다시 불러오기**를 먼저 누름. 전체 새로고침 전에 저장 상태 확인 |
| 터미널 연결 끊김 | **다시 연결**, 필요하면 `+` 새 터미널. 기존 서버가 살아 있는지 확인한 뒤 재실행 |
| 비활성 상태 / 일시정지 | **계속 작업** 또는 입력으로 연결. 작업 환경의 일시정지와 응시 타이머 정지를 구분 |
| 웹캠·휴대폰·화면 공유 끊김 | **감독 연결 → 연결 확인**에서 해당 장치 복구. 화면 공유는 전체 화면, 휴대폰은 현재 PC의 연결 QR을 Proctor 앱으로 다시 스캔 |
| 응시 탭을 실수로 닫음 | 본인의 같은 링크로 재입장 → 웹캠·전체 화면 공유·Proctor 재연결. 저장된 파일로 재개, 미저장 수정은 보장되지 않음 |

복구·문의 중에도 타이머는 흐른다. 반복 장애는 상단 **문제 신고**에서 유형을 고르고 `발생 시각 / 단계 / 직전 동작 / 오류 문구`를 적는다. 키·토큰은 넣지 않는다. 후속 문항 오류면 문항 번호를 포함하고, 별도 신고 버튼이 없는 문항 창에서 상단에 접근하기 어렵다면 발생 내용을 기억해 신고 가능한 경로를 따른다. 감독 경고 자체가 즉시 탈락을 뜻하지 않으므로 화면 안내대로 복구한다. [상세 가이드 p.5]

다운로드와 시작 요청은 [README](../README.md)의 순서로 돌아간다. 과제 폴더에서 `.cofa-kit` 안으로 `cd`하지 않는다. 기존 폴더가 있으면 [충돌·업데이트 설명](MANUAL.md#4-3-cofa-kit이-이미-있는-경우)을 따른다. 시험 중에는 Git Push, 개인 PC 파일 업로드, 문제·파일·결과의 외부 전송, Computer Use를 하지 않는다.
